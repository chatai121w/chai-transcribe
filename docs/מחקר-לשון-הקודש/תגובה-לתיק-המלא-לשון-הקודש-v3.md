# תגובה לתיק המלא לשון הקודש, גרסה 3

תאריך בדיקה: 2 בספטמבר 2026  
נבדק מול עץ העבודה המקומי הנוכחי של `chai-transcribe`.  
לא בוצעו שינויי קוד במסגרת הבדיקה.

## הכרעה

גרסה 3 היא הגרסה הטובה והמדויקת ביותר עד כה. היא קיבלה נכון את חמש הערות הדיוק מגרסה 2, שדרגה בצדק את ראיית באג המיסוך מהרצת סימולציה לשחזור בצינור האמיתי, והוסיפה ממצא תקף לגבי נרמול מנצפ"ך ומתג `general`.

המסמך כבר מתאים לשמש בסיס לביצוע. לפני שמקפיאים אותו כמסמך קנוני, מומלץ לבצע ארבעה תיקוני ניסוח ומעמד. אין צורך בסבב חקירה נוסף לפני תחילת העבודה.

## מה התקבל במלואו

### hotwords

הניסוח החדש נכון כמעט לחלוטין:

- התקרה חלה לאחר deduplication.
- בהתקנה טרייה מונחי LK יכולים להיכנס.
- context boost עשוי להציל מונח.
- מונח שחופף למקור בעל ציון גבוה נשאר בציון הגבוה.
- אין מכסה ואין דיווח dropped.

גם הטבלה `0-60 לפי תחרות ו-context` מדויקת בהרבה מהניסוחים הקודמים.

### מעמד ראיית המיסוך

העדכון נכון. הממצא אינו עוד סימולציה בלבד:

- הוא שוחזר דרך `applyTranscriptionKnowledge` האמיתית.
- הוכח שתיקון learned יכול לחסום כלל רב-מילי.
- הוכח שתיקון תקין במקום אחד יכול למסך occurrence מקורי במקום אחר.
- הטסטים הזמניים הוסרו ולכן עדיין חסר regression test קבוע.

זהו P0 מאומת.

### נתוני SQLite

הסייג החדש נכון: המספרים מתארים את `server/lk_data.db` במחשב שנבדק בלבד. אין להסיק מהם על ענן, מחשב אחר או התקנה ישנה.

### הקוד הישן

הסייג לגבי 11 מסלולים נכון. הם אינם נצרכים על ידי ה-client הפעיל בריפו, מלבד השימוש החי ב-GET של המילון לצורך ייבוא legacy. אין בכך הוכחה שאין צרכן חיצוני.

### נרמול מנצפ"ך ו-`general`

הממצא החדש מאומת:

1. כללי ההחלפה עוברים דרך category toggle.
2. נרמול מנצפ"ך רץ לאחר הלולאה ללא בדיקת category.
3. השינויים שלו מדווחים כ-`general`.
4. לכן כיבוי `general` אינו תואם למה שהלוג וה-UI מבטיחים.

זו סתירת חוזה אמיתית. הפתרון המועדף הוא קטגוריה נפרדת בשם `orthography`, עם toggle עצמאי וברירת מחדל השומרת על ההתנהגות הקיימת. חיבורו ל-`general` אפשרי, אך מערב שני סוגים שונים של ידע.

## ארבעה תיקונים אחרונים

### 1. נתיב Gold ללא ענן

המשפט הבא רחב מדי:

> כשה-`isCloud` כבוי, כל ההגנה נעקפת בשקט.

בפועל רק ענף **שמירת מקור ה-Gold בענן** נעקף. שאר ההגנות ממשיכות לפעול:

- נדרש קובץ מקור.
- נדרש טקסט אמת.
- נדרשים word timings או קטע מתוזמן ידנית.
- `assessReferenceSegment` בודק סבירות.
- קטע האודיו נשלח ל-`/training/dataset/approved-pair` ונשמר בדאטהסט המקומי.
- קיימת מניעת כפילויות בשרת האימון.

בנוסף, במסמך נכתב שיש "שלוש נקודות throw", אך בקטע המצוטט יש שתי פקודות `throw`; `waitForAudioUpload: true` הוא מנגנון המתנה/חוזה, לא throw שלישי בפני עצמו.

הניסוח המומלץ:

> כאשר `isCloud` כבוי, בדיקות האיכות ושמירת קטעי Gold המקומיים עדיין פועלות, אך שמירת קובץ המקור המלא בענן והבטחת זמינות ממכשיר אחר אינן מתבצעות. המצב צריך להיות מסומן במפורש כ-`local-only`.

מבחינת עדיפות, אין צורך לחסום Gold מקומי אם שרת האימון שומר את הקטעים בדיסק. עדיף:

1. להציג `Gold מקומי בלבד`.
2. לשמור `storageScope: local | cloud` במטא-דאטה.
3. להציע פעולת גיבוי לענן.
4. לחסום רק כאשר גם השמירה המקומית של קטע האודיו נכשלה.

זו בעיית שקיפות ושרידות, לא בהכרח P0, כל עוד ה-Gold המקומי כולל אודיו קריא.

### 2. נקודת 60 התיקונים הנלמדים

המשפט "כ-60 תיקונים נלמדים ייחודיים מספיקים כדי לאפס את LK" נכון תחת תנאים שחייבים להיכתב:

- כל 60 הפלטים ייחודיים לאחר normalization.
- הם אינם חופפים למונחי LK.
- אין מונח LK שמקבל context boost גבוה מספיק.
- אין manual/profile/vocabulary שמשנים את הרכב 60 המקומות באופן שמחזיר מונח חופף.

הניסוח המדויק:

> 60 פלטי learned ייחודיים, שאינם חופפים ל-LK ואינם מפנים מקום דרך deduplication, יכולים לבדם למלא את כל התקציב ולדחוק את מונחי LK שלא קיבלו context boost.

זה אינו מחליש את הממצא. הוא הופך אותו לטענה הניתנת לבדיקה מדויקת.

### 3. טבלאות SQLite ריקות אינן בהכרח באג

בטבלת המספרים `lk_dictionary` ו-`lk_sessions` מסומנות באדום. אפס שורות הוא ממצא עובדתי, אך אינו באג בפני עצמו.

הוא הופך לכשל רק אם המוצר מצפה שהנתיבים הפעילים יכתבו לטבלאות האלה. מאחר שה-UI הישן מנותק והמעבדה משתמשת כיום במאגרים חדשים, טבלאות ריקות עשויות להיות תוצאה צפויה של ארכיטקטורה שנטשה את המסלול הישן.

מומלץ לסמן אותן:

```text
סטטוס: observed / legacy-unused
```

ואז לקבל החלטה מפורשת:

- migrate and retire.
- reconnect.
- delete after export/backup.

אין לבנות עליהן לולאת למידה חדשה לפני ההכרעה.

### 4. מיקום מדיניות Gold בסדר העדיפויות

ב-P0 נכתב:

> נתיב Gold לא-ענן: או לחסום, או להצהיר במפורש כ-local-only.

שני חלקי המשפט אינם שווי חומרה:

- שמירת Gold ללא אודיו קריא היא P0.
- שמירת Gold עם אודיו מקומי תקין אך ללא ענן היא מצב מוצר לגיטימי, בתנאי שהוא מסומן בבירור.

לכן מומלץ לפצל:

- P0: לעולם לא לאשר Gold אם כתיבת קטע האודיו נכשלה.
- Quick win: להציג ולשמור `local-only` כאשר אין גיבוי ענן.
- P1: גיבוי וסנכרון Gold בין מכשירים.

## הערות על סדר העבודה

### שלב 0 נכון וחיוני

הוספת הטסטים לפני התיקון היא ההחלטה החשובה ביותר במסמך. יש להכניס אותם כשהם נכשלים, לא לתקן קודם ואז לכתוב טסט שעובר.

הסט המינימלי:

1. learned משנה occurrence אחד, occurrence זהה אחר אינו מוגן.
2. כלל רב-מילי משנה טוקן סמוך ומשאיר טוקן מוגן ללא שינוי.
3. גבול ימין אינו מאפשר התאמה בתוך מילה עברית ארוכה.
4. ייבוא legacy פעמיים אינו משנה `verified` ואינו יוצר שינוי נוסף.
5. PATCH דוחה regex שבור ושומר את הכלל הקודם.
6. תקציב מלא עדיין מקצה לפחות K מקומות ל-LK.
7. כיבוי `orthography` או `general`, לפי ההחלטה, תואם את השינויים המדווחים.

### matcher מרכזי

המסמך צודק שאין ליישם את וריאנט B כ-regex מקומי נוסף. הדרך הנכונה:

```ts
type ProposedEdit = {
  layer: string;
  sourceSpan: { start: number; end: number };
  beforeTokens: string[];
  afterTokens: string[];
  protectedTokenIds: string[];
  precedence: number;
  reason: string;
};
```

ה-arbiter בודק אילו טוקנים באמת משתנים, ולא אם כל span חופף למשהו מוגן.

### בדיקות סתירה בין שכבות

הסעיף החדש טוב ומומלץ להרחיבו למטריצה מלאה:

| שכבה מוקדמת | שכבה מאוחרת | מה בודקים |
|---|---|---|
| learned | LK | הגנה מקומית וכלל רב-מילי |
| learned | vocabulary | occurrence בלתי קשור |
| learned | profile | precedence לפי דובר |
| learned | definitive | תיקון אנושי מול כלל מוחלט |
| LK | vocabulary | שתי וריאציות לאותו מקור |
| vocabulary | profile | ידע כללי מול ידע דובר |
| profile | definitive | כלל דובר מול כלל מערכת |
| category toggle | audit | שליטה ודיווח תואמים |

לכל תא נדרש לפחות טסט conflict אחד וטסט non-conflict אחד.

## סדר עדיפויות סופי

### P0

1. regression tests לבאגי שלמות הטקסט.
2. masking לפי occurrence עם provenance.
3. הכרעת edits המאפשרת שינוי בטוקן סמוך.
4. גבול מילה סימטרי.
5. monotonic trust ו-idempotency בייבוא legacy.
6. איסור Gold אם שמירת קטע האודיו נכשלה.

### Quick wins

1. hotwords לשתי זרימות Groq.
2. `customVocabulary` ל-Gemini הראשי.
3. regex validation ב-PATCH.
4. תיקון חיתוך רשימת hotwords בבנצ'מרק הישן.
5. קטגוריית `orthography` ומתג תואם.
6. סימון `Gold local-only`.
7. לוג `executionPhase`, `precedence`, conflicts ו-dropped terms.

### P1

1. מכסות מקור ב-hotwords.
2. benchmark קנוני במעבדה בלבד.
3. `speakerId` נפרד מ-`groupId`.
4. חיבור דגימות פרופיל ל-snapshot רק עם אודיו קריא.
5. סנכרון וגיבוי Gold בין מכשירים.
6. מטריצת בדיקות סתירה בין שכבות.

### P2

1. הכרעה על הקוד והטבלאות הישנים.
2. הפרדת normalization לפי comparison, identity ו-matching.
3. סגירת חיבורי SQLite מפורשת.
4. איחוד helpers לאחר profiling.

## האם המסמך מוכן למסירה

כן. גרסה 3 מוכנה למסירה למפתח ולתחילת יישום. ארבעת התיקונים המוצעים כאן אינם דורשים חקירה חדשה, אלא עריכת ניסוח ותיעדוף.

הנחיית הביצוע המומלצת:

> השתמש ב-v3 כמפת העבודה. תקן תחילה את ניסוח Gold ואת תנאי 60 ה-hotwords, הכנס את טסטי הכשל הקבועים, ואז טפל ב-P0 לפי הסדר. אל תתחיל באיחוד קוד legacy או באימון מודל לפני שהצינור הדטרמיניסטי ונתוני Gold מוגנים.

- אומתו מחדש ענפי `persistGoldSource` ו-`approveGold`.
