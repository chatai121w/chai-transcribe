# תגובה לסבב השלישי: מערכת לשון הקודש

תאריך בדיקה: 2 בספטמבר 2026  
היקף: בדיקה מול הקוד הנוכחי בריפו, ללא שינויי קוד.

## מסקנה מנהלית

הביקורת בסבב השלישי חזקה וברובה נכונה. היא מתקנת היטב כמה אי-דיוקים מהסבבים הקודמים ומזהה שתי בעיות אמיתיות: מנגנון ההגנה על תיקונים נלמדים עלול לשבור כללים רב-מיליים, וסדר `changes` אינו משקף את סדר הביצוע.

עם זאת, הפתרון המוצע של "הגנה לפי טווחי תווים ודילוג על כל התאמה שחופפת לטווח מוגן" אינו מספיק. הוא שומר על הרצף הטקסטואלי, אך עדיין עלול לחסום כלל רב-מילי שלם כאשר רק מילה אחת בתוכו מוגנת. הפתרון המקצועי הוא מעבר להצעות עריכה עם provenance ברמת טוקן והכרעת התנגשויות מרכזית.

## בעיית ה-masking

המימוש הנוכחי מגן על פלטים של תיקונים נלמדים באמצעות החלפה גלובלית בטוקן זמני. לדוגמה:

```text
טקסט גולמי: פידיון הקדיש
תיקון נלמד: פידיון -> פדיון
כלל לשון הקודש: פדיון הקדיש -> פדיון הקדש
```

לאחר התיקון הנלמד מתקבל `פדיון הקדיש`. כאשר `פדיון` מוחלף בטוקן מוגן, מנוע הכללים אינו רואה עוד את הביטוי `פדיון הקדיש`, ולכן אינו יכול לתקן את `הקדיש`.

### מדוע טווחי תווים בלבד אינם מספיקים

אם המנוע ידלג על כל כלל שחופף לטווח המוגן של `פדיון`, הוא עדיין ידלג על כל הביטוי ולא יתקן את `הקדיש`. בנוסף, טווחי תווים משתנים לאחר כל עריכה מוקדמת, ולכן הם דורשים ניהול offsets מורכב ועלולים להפוך ללא תקפים.

### הפתרון המומלץ

לבנות מסלול של הצעות עריכה ולא מסלול של החלפות טקסט עוקבות:

```ts
type ProposedEdit = {
  layer: string;
  startToken: number;
  endToken: number;
  before: string[];
  after: string[];
  confidence?: number;
  priority: number;
  reason: string;
};
```

1. הטקסט מפוצל פעם אחת לטוקנים עם מזהים יציבים.
2. כל שכבה מציעה edits ואינה משנה מיד את הטקסט.
3. תיקון נלמד מסמן רק את הטוקנים שהוא שינה, ולא כל הופעה של הפלט.
4. כלל רב-מילי רשאי להציע שינוי לחלק הלא מוגן של הביטוי.
5. arbiter מרכזי מכריע בהתנגשויות לפי מקור, confidence, עדיפות וחפיפת הטוקנים.
6. רק לאחר ההכרעה מחילים את כל העריכות במעבר אחד.

בכך נשמר הכלל החשוב: תיקון אנושי מאומת אינו נדרס, אך הוא גם אינו מסתיר הקשר נחוץ מכללים אחרים.

## לוגים וסדר ביצוע

המסמך צודק שסדר `changes` הנוכחי עלול להטעות. עם זאת, שינוי סדר המערך בלבד אינו מספיק, משום שקיימים שני סדרים שונים:

- `executionPhase`: מתי השכבה רצה.
- `precedence`: מי מנצח כאשר יש התנגשות.

לדוגמה, learned רץ ראשון אך הפלט המוגן שלו משוחזר אחרון ולכן הוא בעל קדימות גבוהה. מומלץ שלכל אירוע יהיו שדות מפורשים:

```json
{
  "layer": "learned-correction",
  "executionPhase": 10,
  "precedence": 100,
  "status": "applied",
  "reason": "human_verified",
  "inputSpan": [12, 13],
  "outputSpan": [12, 13]
}
```

אין להסיק סדר כרונולוגי ממיקום איבר במערך.

## תקציב ה-hotwords

בקוד קיימת תחרות על רשימה סופית של עד 60 מונחים. המקורות מקבלים ציונים שונים, ובפרט learned מקבל משקל גבוה יותר מ-LK. אין מכסות מינימום לפי מקור ואין דיווח ברור אילו מונחים נפלו ולמה.

ההמלצה:

1. להגדיר מכסת מינימום קטנה למקורות קריטיים, למשל LK ופרופיל הגייה.
2. למלא את יתר התקציב לפי דירוג מאוחד, תדירות, רלוונטיות לנושא וקרבה להקשר.
3. להסיר כפילויות לאחר נורמליזציה, לפני חישוב התקציב.
4. לרשום לוג לכל מקור: candidates, selected, deduplicated, dropped ו-reason.
5. להציג ב-Experiment Run את ההקשר שנשלח בפועל לכל ספק, ולא רק את ההקשר שנבנה לפני חיתוך.

הביטוי "learned מנצח פעמיים" שימושי כתיאור סיכון, אך חשוב לאחד תצפית ולא את המנגנונים: בחירת hotwords והכרעת תיקוני post-processing צריכות להישאר שכבות נפרדות עם מדדים נפרדים.

## חיבור הזרימות הראשיות

נמצאו חוסרים ב-`Index.tsx` לעומת `LiveTranscriber` והמעבדה. זהו Quick win, אך אינו רק הוספת שורה אחת:

- Groq מצפה ל-hotwords בפורמט המתאים ל-FormData.
- Gemini משתמש ב-`customVocabulary` במבנה אחר.
- יש לכבד את מצב לשון הקודש, פרופיל ההגייה והמילונים שהמשתמש הפעיל.
- יש לבדוק את payload בפועל ולא רק את בניית רשימת המונחים.
- יש לתעד אילו מונחים נשלחו ואילו הושמטו.

מומלץ לחלץ API משותף קטן:

```ts
buildProviderContext({ provider, language, profile, enabledSources })
```

הפונקציה תחזיר payload ספק-ספציפי וגם metadata אחיד ללוג. המסך הראשי ומעבדת התמלול ישתמשו באותו builder, בעוד ניהול הניסוי והשוואת המודלים יישארו במעבדה.

## תכנית עבודה מומלצת

### P0: שלמות נתונים וטקסט

1. להחליף masking גלובלי במודל הצעות עריכה ברמת טוקן.
2. לקבוע arbiter אחד לכל שכבות התיקון ולתעד precedence מפורש.
3. להוסיף בדיקות לאי-דריסת תיקון אנושי ולכללים רב-מיליים.
4. לשמור provenance מלא לכל Gold ולמנוע זליגה בין train ל-evaluation.

### Quick wins במקביל

1. לחבר hotwords לזרימות Groq החסרות ב-`Index.tsx`.
2. לחבר `customVocabulary` לזרימת Gemini הראשית.
3. להפוך את סדר הלוג למפורש באמצעות `executionPhase` ו-`precedence`.
4. להוסיף לוג של dropped hotwords לפי מקור וסיבה.

### P1: מדידה מקצועית

1. benchmark ראשי: אותו דובר, הקלטות חדשות ומופרדות בזמן.
2. benchmark משני: דובר חדש מאותו סגנון.
3. benchmark נוסף: מקור או נושא חדש.
4. למדוד WER, CER, Term Recall, substitutions תורניים ופגיעה במילים תקינות.
5. להפריד תוצאות ASR גולמי מתוצאות post-processing.

### P2: איחוד ותחזוקה

1. לאחד את מנגנוני הקריאה וה-cache רק לאחר profiling של המסלולים החמים.
2. להסיר שכבות legacy רק לאחר import ובדיקת שקילות.
3. להחליף ספירות בינאריות בדיווח מספר השינויים האמיתי לכל שכבה.
4. להציג ב-UI מקור, גרסה, הגדרות ו-context לכל תמלול.

## בדיקות קבלה הכרחיות

1. `פידיון הקדיש` עם learned `פידיון -> פדיון` וכלל `פדיון הקדיש -> פדיון הקדש` חייב להסתיים כ-`פדיון הקדש`.
2. כאשר אותה מילה נכונה מופיעה פעמיים ורק הופעה אחת תוקנה, רק ההופעה שתוקנה מקבלת הגנה.
3. כלל מאוחר אינו רשאי לשנות טוקן שסומן `human_verified`, אך רשאי לשנות טוקן סמוך באותו ביטוי.
4. לוג מציג בנפרד סדר הרצה וסדר קדימות.
5. כאשר יש יותר מ-60 מועמדים learned, עדיין נשמרת מכסת LK מוגדרת.
6. payload של Groq ושל Gemini נבדק בבדיקת integration לכל זרימה ראשית.
7. benchmark אינו כולל אותו קובץ, קטע חופף או תיקון ששימש לאימון.
8. תוצאה נשמרת עם גרסת מנוע, גרסת כללים, hash של מילון וגרסת Context Pack.

## הכרעה

אפשר לקבל את רוב מסקנות הסבב השלישי, אך לא ליישם את הצעת ה-range masking כפי שהיא. היא תיקון חלקי שעלול להנציח את הכשל הרב-מילי בצורה אחרת.

הצעד הנכון הוא לבנות מנגנון מרכזי של הצעות עריכה והכרעת התנגשויות ברמת טוקן, ובמקביל לבצע את תיקוני החיבור הקטנים ל-Groq ול-Gemini ואת שיפור הלוגים. כך מתקבלת מערכת שניתנת למדידה, להסבר ולשיפור בלי שכל שכבה תדרוס או תסתיר את האחרת.

## מה בוצע בבדיקה זו

- המסמך שסופק נקרא ונותח מול הקוד הנוכחי.
- אומתו סדר הצינור, מנגנון ה-masking, סדר `changes`, נקודות שליחת Groq ומבנה תקציב ה-hotwords.
- נבדקו נקודות הקריאה של `transcriptionPipeline` והפרדת המעבדה מהמסך הראשי.
- לא בוצעו שינויי קוד ולא הופעלו מיגרציות.
