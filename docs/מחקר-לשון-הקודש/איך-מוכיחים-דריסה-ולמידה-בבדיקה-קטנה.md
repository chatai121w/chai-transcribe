# איך מוכיחים דריסה ולמידה בבדיקה קטנה

תאריך: 2 בספטמבר 2026

## התשובה הישירה

אתה צודק. **דריסה, שמירה והפעלה של תיקון הן עובדות שאפשר לבדוק בדוגמה קטנה.**
אין צורך במחקר גדול כדי לדעת אם תיקון נשמר ואם כלל אחר דורס אותו.

הבלבול נוצר משום שיש ארבע שאלות שונות:

1. האם התיקון נשמר?
2. האם התיקון מוחל בריצה הבאה?
3. האם שכבה אחרת דורסת אותו?
4. האם המודל האקוסטי למד לזהות את הצליל גם בהקלטות חדשות?

את שלוש הראשונות אפשר להוכיח מיד בדוגמאות קטנות. רק הרביעית דורשת הרבה
דוגמאות ומבחן חדש.

## בדיקה 1: האם התיקון נשמר?

לדוגמה:

```text
שגוי: ארומך
נכון: ארוממך
```

הבדיקה:

1. שומרים `ארומך → ארוממך` דרך הממשק.
2. קוראים מיד את מאגר התיקונים ומוודאים שהזוג נמצא פעם אחת.
3. מרעננים את הדף וקוראים שוב.
4. פותחים session חדש וקוראים שוב.
5. אם נדרש סנכרון ענן, קוראים גם ממכשיר או browser context אחר.

תוצאה אפשרית:

- נמצא לפני ואחרי רענון: נשמר מקומית.
- נמצא גם במכשיר אחר: נשמר בענן.
- נעלם אחרי רענון: לא נשמר באמת.

זו בדיקה חד-משמעית.

## בדיקה 2: האם התיקון מופעל?

אין צורך אפילו באודיו. נותנים ישירות לצינור את פלט המנוע הגולמי:

```text
קלט: ארומך אלוהי המלך
תיקון שמור: ארומך → ארוממך
פלט צפוי: ארוממך אלוהי המלך
```

אם הפלט אינו צפוי, בודקים את הסיבה:

- התיקון מתחת לסף confidence.
- מנגנון הלמידה כבוי.
- המנוע או הפרופיל אינם תואמים.
- המאגר הלא נכון נטען.
- התיקון נשמר כ-Candidate ולא כ-Verified.

גם זו עובדה דטרמיניסטית.

## בדיקה 3: האם שכבה אחרת דורסת?

יוצרים בכוונה התנגשות:

```text
תיקון אנושי: ארומך → ארוממך
כלל LK סותר: ארוממך → ארוממך-שגוי
קלט: ארומך אלוהי המלך
פלט צפוי לפי המדיניות: ארוממך אלוהי המלך
```

מריצים בנפרד:

1. רק Learned.
2. Learned + LK.
3. Learned + LK + Vocabulary.
4. Learned + LK + Vocabulary + Profile.
5. כל השכבות + Definitive.
6. כל השכבות + AI.

ברגע שבשלב מסוים הפלט משתנה ל-`ארוממך-שגוי`, יודעים בדיוק איזו שכבה דרסה.

למעשה, הבדיקה הקיימת בפרויקט כבר מוכיחה מקרה אחד: תיקון אנושי
`ארומך → ארוממך` נשאר מול כלל LK סותר. היא עברה. אבל היא אינה מוכיחה את כל
זוגות השכבות ואינה בודקת AI.

## בדיקת באג המיסוך

גם את באג המיסוך אפשר להוכיח ללא אודיו:

```text
תיקון נלמד: היא → הוא
כלל LK: הוא ביטוי → ביטוי מתוקן
קלט: היא ביטוי, וגם הוא ביטוי
```

הכוונה היא להגן רק על ה-`הוא` שנוצר מהתיקון הראשון. אבל המימוש הנוכחי
ממסך לפי ערך המילה בכל הטקסט, ולכן הוא עלול להגן גם על ה-`הוא` השני ולמנוע
מכלל LK לפעול עליו.

בדיקה נכונה צריכה לשמור offsets או spans ולדרוש:

- המופע שנוצר מתיקון אנושי נשמר.
- המופע האחר ממשיך לעבור בכלל LK.
- שום placeholder אינו נשאר בפלט.

זו תקלה עובדתית, לא שאלה סטטיסטית.

## היכן האודיו כן נחוץ

האודיו נחוץ כאשר רוצים לבדוק את כל המסלול כפי שהמשתמש מפעיל אותו:

```text
אודיו
→ מנוע תמלול
→ פלט גולמי
→ תיקונים נלמדים
→ LK ומילון
→ פלט סופי
```

הבדיקה שהצעת נכונה:

1. מעלים הקלטה קצרה עם מילה מומצאת או נדירה.
2. שומרים את הפלט הגולמי.
3. מתקנים ומאשרים את המילה.
4. מעלים שוב בדיוק את אותה הקלטה.
5. משווים את הפלט הגולמי ואת הפלט הסופי.
6. מעלים הקלטה חדשה של אותה מילה.
7. מרעננים וטוענים שוב את ה-Gold.

אבל חשוב לפרש נכון את התוצאות.

## ארבע תוצאות שונות

### מצב א: הפלט הגולמי נשאר שגוי, והפלט הסופי תוקן

```text
Raw:   ארומך
Final: ארוממך
```

המילון או post-processing למדו. **המודל האקוסטי לא למד.**

### מצב ב: אחרי אימון LoRA גם הפלט הגולמי תוקן

```text
Raw לפני אימון: ארומך
Raw אחרי אימון: ארוממך
```

כאשר כל המילונים וכללי הטקסט כבויים, זו ראיה שהמודל או adapter האקוסטי
השתנה.

### מצב ג: אותה הקלטה תוקנה, אבל הקלטה חדשה לא

ייתכן שהמערכת זכרה את הקובץ, cache, fingerprint או תבנית צרה. עדיין לא הוכחה
למידה שמכלילה.

### מצב ד: גם הקלטה חדשה, דובר חדש והקשר חדש תוקנו

זו ראיה חזקה שהלמידה מכלילה.

## למה אותה הקלטה אינה מספיקה ללמידת קול

אותה הקלטה מצוינת לבדיקת רגרסיה, אך היא אינה אומרת מה גרם לשיפור.

ייתכן שהמערכת:

- השתמשה בתיקון טקסט.
- שלחה hotword למנוע.
- החזירה תוצאה מ-cache.
- הפעילה כלל LK.
- השתמשה בפרופיל דובר.
- טענה מודל LoRA חדש.

לכן בכל ריצה צריך לשמור שני שדות נפרדים:

```text
rawTranscript       = מה שהמנוע החזיר לפני כל תיקון
finalTranscript     = מה שהמערכת הציגה אחרי כל השכבות
```

בלעדיהם אי אפשר לדעת אם הקול נלמד או שהטקסט תוקן לאחר התמלול.

## בדיקת העובדות המלאה שצריך לבנות

### A. בדיקת שמירה

```text
שמור → קרא מהמאגר → רענן → קרא שוב → פתח session נוסף → קרא שוב
```

בודקים בנפרד:

- תיקון נלמד.
- מילון Verified.
- פרופיל.
- Human Review.
- Gold עם קטע האודיו.

### B. מטריצת דריסות

| שכבה מוקדמת | שכבה מאוחרת | מה צריך לנצח |
|---|---|---|
| Learned מאומת | LK | Learned |
| Learned מאומת | Vocabulary | לפי אותה החלטה קנונית; אסור שתהיה סתירה |
| Vocabulary Verified | Profile | מדיניות מפורשת לפי דובר |
| Profile מאומת | Definitive | תיקון אנושי לפי מופע |
| תיקון אנושי | AI | התיקון האנושי נעול |

לכל תא בטבלה יוצרים בדיקה קטנה עם מילה מומצאת, כך ששום ידע קיים אינו משפיע.

### C. בדיקת אודיו מקצה לקצה

לכל הקלטה שומרים:

- checksum של האודיו.
- model/version.
- כל toggles והמילונים.
- `rawTranscript`.
- כל שינוי עם layer ו-rule ID.
- `finalTranscript`.
- החלטת האדם.
- האם נוצר Gold והאם קטע האודיו קריא.

### D. בדיקת למידה אקוסטית

מריצים את אותו Benchmark פעמיים כאשר כל שכבות הטקסט כבויות:

```text
מודל בסיס + knowledge OFF
מודל LoRA  + knowledge OFF
```

רק ההפרש הזה מודד מה המודל למד מהקול.

לאחר מכן מריצים בנפרד:

```text
מודל בסיס + knowledge ON
מודל LoRA  + knowledge ON
```

וכך רואים כמה מהשיפור מגיע מהמודל וכמה מהמילון.

## למה נוצר עד עכשיו מצב של אי-ודאות

לא מפני שאי אפשר לבדוק. הסיבות הן מבניות:

1. קיימים כמה מאגרי תיקונים נפרדים.
2. אותו תיקון יכול להישמר ביותר ממקום אחד.
3. לא בכל מסך נשמרים גם raw וגם final.
4. Human Review, מילון ו-Gold הן פעולות שונות.
5. בדיקות עם mocks מוכיחות את חוזה הממשק, לא את Supabase ו-CUDA האמיתיים.
6. קיימת בדיקה להתנגשות אחת, אך עדיין אין מטריצה מלאה לכל השכבות.

כל אלה פתירים בבדיקות קטנות. אין כאן מגבלה מחקרית.

## המסקנה

ההצעה שלך היא הדרך הנכונה:

```text
מילה מומצאת
→ שמירה
→ רענון
→ אותה הקלטה
→ הקלטה חדשה
→ הפעלת שכבות אחת-אחת
→ בדיקת Raw מול Final
→ בדיקת Gold
```

כך מקבלים תשובה עובדתית לכל שלב.

הדבר היחיד שאי אפשר להוכיח מדוגמה אחת הוא שהמודל השתפר **בכלל המקרים**.
אבל בהחלט אפשר להוכיח בדוגמה אחת אם תיקון נשמר, הופעל, נדרס או נשמר ב-Gold.
